## Root Cause (для находки, вызвавшей FAIL)

`_sanitize_base_url` срезал query-строку и user-info только у URL, разбирающихся как `scheme://netloc`. Для значения вида `user:TOKEN@host/v1` срабатывала «мягкая» ветка, и секрет уходил в тело ответа `GET /api/v1/compare/config`. Три варианта опечатки (битый IPv6, нечисловой порт, порт вне диапазона) роняли необработанный `ValueError` → HTTP 500 на всём эндпоинте.

**Первопричина — в спецификации, не в исполнении:** требование «срезать query и user-info» не определяло поведение для URL, который не разбирается вовсе. Исправлено правилом fail-closed: не парсится начисто → `base_url = None`, переменная уходит в `missing`.

## Lessons Learned

- **Чекпоинт плана окупился до написания кода.** Четыре блокирующие находки об окружении — включая риск наложения 62 чужих миграций на базу движка — стоили одного круга проверки вместо повреждённой БД.
- **Тест, который не падает от мутации, ничего не охраняет.** Ревью доказало мутацией, что append-only проверялся только для отчётов, хотя выглядел покрытым для всех трёх таблиц. Проверка через геттер с `max(revision)` прячет перезапись; ловит только прямое чтение хранилища.
- **FAIL стоит классифицировать, а не сразу чинить.** Дефект оказался в спецификации (неопределённое поведение для непарсящегося URL), а не в аккуратности исполнителя — правило поправлено в спеке, и повторной такой ошибки в стадиях 2–7 не будет.
